Modules MAP et Transports du plugin The Core - Collectivity Management

Version du manuel: 10 avril 2026
Version du plugin: 1.0.1-beta.34
Public visé: équipes éditoriales, chefs de projet, intégrateurs Elementor, administrateurs WordPress

Objectif de ce document
Ce manuel explique comment utiliser les deux modules les plus structurants du plugin:

  • le module MAP, pour gérer des lieux, circuits, balades, randonnées et affichages cartographiques interactifs;
  • le module Transports, pour gérer des lignes, arrêts, parkings, horaires GTFS et données temps réel.

Le document est volontairement orienté usage. Il ne décrit pas l’architecture PHP interne du plugin, sauf quand cela aide à comprendre le fonctionnement côté WordPress ou Elementor.

1. Vue d’ensemble

1.1. Ce que couvre le module MAP

Le module MAP sert à produire des cartes éditoriales réutilisables sur les sites de communes. Il permet d’afficher dans une même carte:

  • des lieux: monument, commerce, plage, office de tourisme, fontaine, point de vue, équipement;
  • des circuits: balade, randonnée, parcours thématique, circuit patrimonial;
  • des lignes de transport si l’option d’intégration avec le module Transports est activée.

1.2. Ce que couvre le module Transports

Le module Transports sert à produire une page transports complète avec:

  • les lignes de transport;
  • les lieux transport: arrêts, parkings, parkings vélos, gares ou points assimilés;
  • les horaires théoriques issus d’un flux GTFS;
  • éventuellement le temps réel si l’opérateur publie un flux compatible.

1.3. Comment les deux modules travaillent ensemble

Les deux modules sont séparés, mais compatibles:

  • le module Transports reste la source de vérité pour les lignes, arrêts et horaires;
  • le module MAP peut inclure des lieux et lignes de transport sur une carte plus éditoriale.

Règle de cadrage
Utilisez Transports pour une page dédiée au réseau et aux horaires. Utilisez MAP pour une carte éditoriale plus large, éventuellement enrichie de transports.

2. Module MAP

2.1. Vocabulaire utile

TermeSignification pratique
LieuPoint géolocalisé: commerce, plage, chapelle, office de tourisme, point de vue, etc.
CircuitParcours éditorial: balade, randonnée, boucle, circuit patrimonial.
Ligne de transportTracé issu du module Transports. Ne pas confondre avec un circuit éditorial.
UniversContexte éditorial du contenu dans la cartographie: patrimoine, itinéraires, tourisme, équipements.
CatégorieNature du contenu: plage, commerce, randonnée, chapelle, restaurant, etc.
ThèmeAxe transverse entre plusieurs contenus du site, par exemple un article, un élément de carte ou un document: patrimoine, nature, tourisme, mobilité, etc.
PublicPublic visé: familles, seniors, touristes, etc.
TerritoireZone géographique ou secteur éditorial.

Univers vs Catégorie
L’univers répond à la question “dans quel grand ensemble éditorial la donnée apparaît-elle ?”. La catégorie répond à la question “qu’est-ce que cet élément est précisément ?”.

Peut-on attribuer plusieurs Univers au même élément ?
Oui. En pratique, un élément peut recevoir plusieurs Univers si cela a un sens éditorial réel. Par exemple, la Maison de Georges Clemenceau peut relever à la fois de patrimoine et de tourisme si vous voulez qu’elle apparaisse dans une carte patrimoine et dans une carte touristique. Il faut éviter d’en mettre plusieurs “par sécurité” : l’intérêt d’un univers est de dire dans quels grands contextes cartographiques un contenu doit ressortir.

2.2. Créer un élément de carte

Chaque lieu ou circuit est créé dans le même type de contenu. C’est le champ Type cartographique qui détermine si l’élément est un lieu ou un parcours.

  1. Dans l’administration WordPress, ouvrir le menu Cartographie > Éléments cartographiques.
  2. Cliquer sur Ajouter.
  3. Saisir le titre WordPress de l’élément.
  4. Dans le bloc Paramètres cartographiques, choisir le Type cartographique : Lieu ou Parcours.
  5. Renseigner les champs communs.
  6. Renseigner ensuite les champs spécifiques au type choisi.
  7. Attribuer les taxonomies utiles : Univers, Catégories, Accessibilité, puis si besoin Thèmes, Publics et Territoires.
  8. Publier ou mettre à jour le contenu.

2.2.1. Champs communs

Dans Paramètres cartographiques, quel que soit le type choisi, l’éditeur renseigne généralement :

  • Titre WordPress: nom de l’élément;
  • Sous-titre: information secondaire affichée dans la vignette;
  • Résumé court: texte bref pour la popup;
  • Libellé CTA et URL CTA: bouton principal éventuel;
  • Ordre d’affichage: utile pour stabiliser certains affichages;
  • Couleur d’accent et Clé icône: réglages de secours si aucun style Elementor ne prend la main;
  • Notes d’accessibilité: texte libre affiché dans la vignette.

2.2.2. Champs d’un lieu

Si Type cartographique = Lieu, l’écran affiche un bloc Coordonnées du lieu avec:

  • latitude;
  • longitude;
  • adresse ou repère;
  • site internet;
  • réseaux sociaux, ajoutables dynamiquement.

Pour chaque réseau social, l’éditeur peut choisir un réseau puis coller l’URL correspondante.

2.2.3. Champs d’un circuit

Si Type cartographique = Parcours, l’écran affiche un bloc Trace du parcours avec:

  • un champ GeoJSON pour coller la géométrie;
  • la distance;
  • la durée;
  • la difficulté;
  • les points liés, utiles pour rattacher des lieux à un circuit.

Les points liés servent à associer au parcours des lieux déjà saisis dans MAP. Cela permet de relier un circuit à ses points d’intérêt ou à ses étapes utiles.

  • sur le plan éditorial, vous donnez du contexte au parcours ;
  • sur la carte, vous reliez un tracé à des lieux concrets déjà existants ;
  • dans la vignette, cela facilite la compréhension de ce que l’usager va trouver sur le trajet.

Exemple : un circuit peut avoir comme points liés :

  • un point de départ ;
  • un dolmen ou une chapelle sur le trajet ;
  • un restaurant ou un commerce utile à l’arrivée.

Point important
Le parcours n’est pas dessiné à la souris dans l’admin. Il faut disposer d’un GeoJSON déjà prêt. Si vous n’avez qu’une trace GPX, il faut d’abord la convertir.

2.2.4. Publications liées

Chaque élément de carte peut embarquer des contenus éditoriaux liés, directement dans sa vignette:

  • Publications principales: boutons forts, avec libellé personnalisable;
  • Publications liées: liens secondaires.

Cas d’usage typique:

  • un circuit de randonnée a une fiche de présentation principale;
  • le même circuit peut aussi être lié à des articles ponctuels: marche citoyenne, actualité locale, reportage photo, etc.

2.3. Taxonomies à renseigner

En plus des champs ci-dessus, l’éditeur attribue des taxonomies:

  • Univers (un ou plusieurs si nécessaire);
  • Catégories;
  • Accessibilité pour le filtre binaire “accessible”;
  • Thèmes, Publics et Territoires si pertinents.

Toutes les taxonomies sont-elles obligatoires ?
Non. Elles sont là pour structurer la donnée quand c’est utile, pas pour alourdir la saisie. Un site peut très bien utiliser seulement Catégories, ou Catégories + Univers, et laisser de côté Thèmes, Publics ou Territoires tant qu’il n’en a pas un besoin éditorial ou fonctionnel clair.

Exemples plus précis :

ÉlémentUniversCatégorieThème
Maison de Georges Clemenceaupatrimoine, tourismemaison-historiquepatrimoine
Plage Clemenceautourismeplagenature, tourisme
Circuit sur les pas de Clemenceauitinéraires, tourismecircuitpatrimoine, tourisme

Lecture correcte de ces trois colonnes :

  • Univers : dans quelle ou quelles cartes thématiques l’élément doit-il apparaître ?
  • Catégorie : qu’est-ce que cet élément est concrètement ?
  • Thème : sous quel angle éditorial transverse veut-on pouvoir le retrouver avec d’autres contenus du site, par exemple des articles, d’autres éléments de carte ou des documents ?

Exemple simple pour le thème :

  • un article d’actualité sur une visite guidée de la Maison de Georges Clemenceau ;
  • la fiche cartographique Maison de Georges Clemenceau ;
  • une brochure PDF de visite ;

Ces trois contenus sont de nature différente, mais ils peuvent partager le même Thème = patrimoine. Le thème sert donc à les retrouver ensemble dans un même axe éditorial.

2.4. Widget Elementor “Carte”

Le widget principal s’appelle Carte. Il porte les données, la carte Leaflet et les principaux réglages d’affichage.

2.4.1. Contrôles de contenu

Le widget permet notamment de:

  • définir un identifiant de groupe pour le relier à d’autres widgets de filtres;
  • préfiltrer la carte par Univers, Catégories, Thèmes, Publics et Territoires;
  • limiter à Accessible uniquement;
  • inclure ou non les transports;
  • limiter les transports à certains modes;
  • afficher ou non les lieux et les parcours;
  • afficher ou non les filtres internes, la recherche et le compteur;
  • définir la hauteur de la carte;
  • choisir le cadrage initial automatique ou manuel;
  • activer, dans Elementor seulement, le debug d’édition.

2.4.2. Styles par catégorie

Chaque catégorie peut recevoir son propre style de marqueur et, pour les parcours, son propre style de tracé:

  • couleur;
  • type d’icône;
  • icône Elementor ou SVG personnalisé;
  • libellé court si vous utilisez un marqueur textuel;
  • épaisseur du tracé;
  • type de trait;
  • position de l’icône sur le parcours;
  • décalage au début et à la fin du tracé.

Bon usage
Les styles par catégorie conviennent quand tous les éléments d’une catégorie doivent partager le même rendu. Dès qu’un parcours doit garder un habillage spécifique, utilisez plutôt les presets de parcours.

2.4.3. Styles des vignettes

Le widget permet aussi de styliser les popups:

  • fond de vignette;
  • couleur du texte principal et secondaire;
  • couleur de bordure;
  • couleurs des liens texte;
  • couleurs des tags;
  • couleurs des pastilles de liens;
  • couleurs des boutons principaux et secondaires;
  • typographies: titre, texte courant, titres de sections, tags, pastilles, boutons.

2.4.4. Styles des parcours

Le widget propose quatre presets de parcours réutilisables. Chaque preset peut définir:

  • couleur;
  • type d’icône;
  • icône Elementor ou SVG;
  • libellé éventuel;
  • épaisseur du tracé;
  • type de trait;
  • position de l’icône principale sur le tracé;
  • décalage en début et fin de tracé;
  • plusieurs icônes supplémentaires, chacune avec sa propre position, taille, couleur et option de contour.

Ensuite, le bloc Affectation des parcours permet d’affecter un preset précis à un circuit ou à une ligne de transport.

Comment lire les décalages de début et fin
Les pourcentages sont relatifs à la moitié du parcours. En pratique, 0 signifie aucun rognage et 100 signifie un rognage jusqu’au milieu du tracé.

2.5. Widgets de filtres séparés

Le module MAP peut être mis en page de deux manières:

  1. avec les filtres directement dans le widget Carte;
  2. avec des widgets séparés pour composer une interface plus libre.

Widgets disponibles:

WidgetUsage
CartePorte la carte, les données et les réglages principaux.
Recherche de carteAffiche uniquement le champ de recherche.
Types de résultatsAffiche uniquement les boutons Lieux, Circuits et Lignes de transport.
Catégories de carteAffiche uniquement les facettes choisies: Univers, Catégories, Thèmes, Publics, Territoires, Modes de transport, Accessible.
Réinitialiser la carteAffiche uniquement le bouton de reset.
Filtres de carteWidget combiné. Utile pour des mises en page plus rapides, mais moins fin qu’un assemblage dédié.

Règle impérative: si vous utilisez des widgets séparés, ils doivent tous partager le même Identifiant de groupe que le widget Carte correspondant.

Exemple de mise en page

  1. Placez un widget Carte avec Identifiant de groupe = carte-svsj.
  2. Désactivez ses filtres internes.
  3. Ajoutez un widget Recherche de carte avec le même identifiant.
  4. Ajoutez un widget Types de résultats avec le même identifiant.
  5. Ajoutez un widget Catégories de carte avec le même identifiant.
  6. Ajoutez un widget Réinitialiser la carte si nécessaire.

2.6. Intégration des transports dans la carte

Le widget Carte peut intégrer des données du module Transports.

  • les arrêts et lieux transport apparaissent comme des points;
  • les lignes transport apparaissent comme des tracés distincts des circuits éditoriaux;
  • le filtre de type distingue désormais Circuits et Lignes de transport.

Cette distinction est importante: un itinéraire touristique ou une randonnée n’a pas le même sens qu’une ligne de bus.

Comportement spécifique

  • un arrêt lié à une seule ligne peut reprendre automatiquement la couleur de cette ligne;
  • les hubs transport sont regroupés pour éviter les doublons dus aux quais ou directions GTFS;
  • les lignes transport peuvent être rognées visuellement via les presets de parcours pour éviter d’envahir toute la commune;
  • si un widget Horaires transport est lié à la carte, la carte peut limiter le tracé à la branche correspondant à la direction sélectionnée;
  • les alertes temps réel de type ServiceAlerts peuvent être signalées visuellement sur les lignes ou arrêts concernés.

2.7. Cas d’usage MAP recommandés

Cas 1 - Carte touristique complète

  • Objectif: offrir sur une seule carte les lieux à voir, les itinéraires utiles et les transports.
  • Univers typiques: tourisme, éventuellement patrimoine et itinéraires.
  • Types affichés: lieux + circuits + lignes de transport.
  • Widgets séparés recommandés: recherche + types de résultats + catégories.
  • Catégories typiques: plage, maison historique, office de tourisme, point de vue, restaurant, commerce.
  • Intérêt: un visiteur prépare ou vit sa visite sans changer de carte selon le besoin.

Cas 2 - Carte spécifique “Où manger à Saint-Vincent-sur-Jard ?”

  • Objectif: créer une carte simple dédiée aux restaurants, commerces alimentaires ou pauses utiles.
  • Univers typique: tourisme.
  • Types affichés: lieux uniquement.
  • Catégories typiques: restaurant, commerce.
  • Intérêt: page courte, lisible, facile à intégrer dans un parcours éditorial “bien manger” ou “adresses utiles”.

Cas 3 - Carte “Balades et circuits à Saint-Vincent-sur-Jard”

  • Objectif: afficher les balades, randonnées et parcours thématiques de la commune.
  • Univers typique: itinéraires.
  • Types affichés: circuits, avec éventuellement quelques lieux liés si cela rend le parcours plus utile.
  • Presets de parcours utilisés pour distinguer randonnée, balade patrimoniale, parcours famille ou boucle courte.
  • Icônes supplémentaires utiles pour marquer départ, belvédère, étape ou arrivée.
  • Option éditoriale possible: afficher aussi quelques restaurants ou commerces liés pour enrichir l’expérience sans brouiller la lecture principale.

2.8. Bonnes pratiques MAP

  • Utilisez Univers pour le contexte éditorial, pas pour décrire la nature précise d’un lieu.
  • Utilisez Catégorie pour décrire ce qu’est l’élément.
  • Réservez les Thèmes à un axe transversal réutilisable sur plusieurs types de contenus.
  • Pour une carte sophistiquée, préférez les widgets de filtres séparés plutôt qu’un seul bloc combiné.
  • Pour les parcours importants, utilisez un preset explicite afin de stabiliser la couleur et les icônes.
  • Quand une ligne transport déborde trop du périmètre communal, ajustez les décalages de début et fin au lieu de modifier la donnée source.

3. Module Transports

3.1. Principes généraux

Le module Transports repose sur deux couches:

  1. une couche éditoriale dans WordPress: lignes et lieux;
  2. une couche horaires importée depuis des flux externes, principalement GTFS.

Cette séparation est importante: on ne stocke pas les horaires dans les champs WordPress des lignes ou des lieux.

Qu’est-ce que GTFS ?
GTFS signifie General Transit Feed Specification. C’est un format standard de données utilisé par les opérateurs de transport pour publier leur réseau. Un flux GTFS contient typiquement les lignes, les arrêts, les trajets, les horaires théoriques et parfois les géométries des parcours.

Dans ce plugin, GTFS sert à éviter une ressaisie manuelle lourde :

  • vous configurez une source opérateur ;
  • le plugin découvre les lignes et les arrêts utiles pour la commune ;
  • il importe ensuite les horaires théoriques dans ses tables techniques ;
  • et il peut aussi utiliser les géométries du feed pour tracer les lignes sur la carte.

Si l’opérateur publie en plus un flux de temps réel, le module peut enrichir la page avec :

  • des prochains départs live ;
  • des perturbations ;
  • des positions de véhicules.

3.2. Les deux types de contenus

ContenuRôleExemples
Ligne de transportDécrit une ligne ou un service de mobilitéLigne 550, navette centre-ville, ligne train
Lieu de transportDécrit un point géolocalisé affiché sur la carteArrêt, gare, parking relais, parking vélo

3.3. La taxonomie “Modes”

Le mode de transport est une taxonomie partagée entre lignes et lieux. Les termes livrés par défaut sont:

  • bus
  • parking
  • velo
  • train

Un arrêt de bus doit donc être assigné au mode bus, un parking vélo au mode velo, etc.

3.4. Configurer une source GTFS

Toute la configuration se fait dans Transports > Horaires.

3.4.1. Paramètres d’une source

Chaque source GTFS possède sa propre fiche de configuration. Les principaux champs sont:

  • Provider label: nom lisible de l’opérateur;
  • Provider key: identifiant technique unique;
  • GTFS ZIP URL: URL du flux statique;
  • Realtime enabled: active ou non l’import temps réel;
  • Realtime format: GTFS-RT, SIRI ou SIRI-Lite;
  • TripUpdates URL, ServiceAlerts URL, VehiclePositions URL selon le fournisseur;
  • Locality name: nom de commune tel qu’il apparaît dans le feed;
  • Locality INSEE si disponible;
  • Extra localities: communes supplémentaires à inclure;
  • Extra route ids: lignes supplémentaires à inclure même hors commune;
  • Extra stop ids: arrêts précis à inclure.

Guide pratique pour remplir ces champs :

ChampQue faut-il mettre ?Où trouver l’information ?

Par où commencer en pratique ?
Le premier réflexe doit être de chercher le réseau ou l’opérateur sur https://transport.data.gouv.fr/. La page du dataset regroupe généralement la ressource GTFS statique, les éventuelles ressources temps réel et des informations de qualité ou de disponibilité. Si rien n’est publié sur le PAN, cherchez ensuite sur le portail open data officiel de la région, de l’AOM ou de l’opérateur.

Exemple concret de méthode :

  1. ouvrir https://transport.data.gouv.fr/ ;
  2. rechercher l’opérateur ou le territoire, par exemple Aléop ou Île-de-France Mobilités ;
  3. ouvrir le dataset concerné ;
  4. copier l’URL de la ressource GTFS pour le champ GTFS ZIP URL ;
  5. si des ressources temps réel existent, copier leurs URLs dans TripUpdates, ServiceAlerts et VehiclePositions ;
  6. ouvrir le ZIP GTFS pour vérifier le nom exact de la commune et, si besoin, les route_id ou stop_id.

Cas multi-opérateurs
Le plugin gère plusieurs sources GTFS en parallèle. Chaque source est isolée par son provider key. Une commune peut donc agréger plusieurs opérateurs sans écraser les données précédentes.

Transfert de configuration entre environnements
Depuis Transports > Horaires, vous pouvez désormais exporter la configuration GTFS au format JSON puis la réimporter sur un autre site. C’est la méthode recommandée pour passer une configuration de dev à préproduction ou production sans tout ressaisir.

Fuseau horaire du site
Les données temps réel reposent en partie sur des timestamps. Elles sont affichées selon le fuseau horaire WordPress du site. Si Réglages > Général > Fuseau horaire reste sur UTC ou sur un décalage gmt_offset = 0, les horaires live et le bloc Dernier passage peuvent apparaître décalés d’une ou deux heures. Pour un site en France, réglez le fuseau sur Paris.

3.4.2. Workflow standard

  1. Créer ou compléter une source GTFS.
  2. Cliquer sur Découvrir et synchroniser.
  3. Vérifier les lignes et lieux créés ou mis à jour.
  4. Cliquer sur Importer les horaires.
  5. Si un flux temps réel existe, cliquer sur Importer le temps réel.
  6. Ouvrir ensuite chaque ligne si nécessaire pour définir les arrêts de référence par direction.

Exemple: Saint-Vincent-sur-Jard

  • éventuellement Extra localities si le besoin est plus large.

3.5. Éditer une ligne de transport

Chaque ligne comporte une fiche avec:

  • Code de ligne;
  • Libellé du trajet;
  • Fréquence;
  • Horaires (résumé éditorial, pas les tableaux GTFS);
  • Mode de gestion: manuel, GTFS ou CSV;
  • Source GTFS;
  • GTFS route_id;
  • GTFS route_short_name;
  • GTFS stop_id suivis;
  • Arrêts de référence par direction;
  • Jours de service;
  • Accessible PMR;
  • Lien externe;
  • Mots-clés de recherche;
  • Ordre d’affichage.

Arrêts de référence
Ce réglage est important pour la page Transports. Il permet de présélectionner un arrêt exact par direction, au lieu d’afficher des horaires ambigus pour une station agrégée.

3.6. Éditer un lieu de transport

Chaque lieu de transport peut représenter un arrêt, un parking, un parking vélo, une gare ou un point assimilé. L’éditeur dispose notamment de:

  • sous-titre;
  • adresse ou description courte;
  • latitude / longitude;
  • GTFS stop_id;
  • Source GTFS;
  • Accessible PMR;
  • Lignes reliées;
  • données parking: type, total, disponibles, PMR, gratuité;
  • données vélo: nombre de vélos, nombre de places, vélos électriques;
  • données train: départs et informations complémentaires.

Le mode de transport n’est pas réglé dans la métabox principale, mais dans la taxonomie Modes.

3.7. Widget Elementor “Transport Explorer”

Le widget dédié aux transports s’appelle Transport Explorer.

3.7.1. Contrôles Elementor

Ses contrôles sont volontairement simples:

  • Titre;
  • Description;
  • Afficher les alertes transport;
  • Afficher tous les véhicules de la ligne sur la carte : si non, la carte ne montre que les véhicules dont le trip dessert au moins un arrêt suivi localement pour la ligne;
  • Animer les déplacements temps réel : interpolation visuelle des véhicules entre deux rafraîchissements;
  • Hauteur carte;
  • une section de style Véhicules temps réel pour régler l’animation, les couleurs, la taille du marqueur et la taille de l’icône.

3.7.2. Comportement côté usager

Le widget affiche:

  • éventuellement des alertes transport;
  • une carte interactive des lignes et lieux de transport;
  • une recherche;
  • des filtres par mode;
  • un panneau bus avec les lignes disponibles;
  • des horaires par direction et par arrêt;
  • un bloc Temps réel quand des prédictions pertinentes existent;
  • des marqueurs véhicules si le flux temps réel fournit des positions compatibles;
  • un regroupement des arrêts proches de type bus pour éviter les doublons entre quais ou directions d’un même arrêt;
  • dans le détail d’une ligne, un bloc Véhicules en circulation filtré par la direction sélectionnée;
  • si l’option est activée, un bloc Progression indiquant si le véhicule approche, est au niveau de l’arrêt ou vient de passer;
  • si l’option est activée, un bouton permettant de sélectionner l’arrêt le plus proche de l’utilisateur via la géolocalisation du navigateur;
  • au clic sur un véhicule, une vignette qui affiche aussi la direction réelle du trajet.

3.7.3. Widget Elementor “Horaires transport”

Le widget Horaires transport permet d’afficher uniquement le panneau d’horaires, sans la carte complète du Transport Explorer. Il est utile quand une page contient déjà une MAP touristique et qu’on veut afficher les horaires de la ligne sélectionnée dans un bloc indépendant.

  • Renseignez le même Identifiant de groupe que le widget Carte pour synchroniser les clics carte et le panneau d’horaires.
  • Activez Limiter la carte à la direction sélectionnée si vous voulez que le tracé de la MAP liée n’affiche que la branche de ligne correspondant à la direction choisie.
  • Activez Afficher la progression pour afficher l’état lisible du véhicule quand les données temps réel fournissent les séquences d’arrêts nécessaires.
  • Activez Proposer l’arrêt le plus proche si vous voulez permettre à l’usager de choisir automatiquement l’arrêt le plus proche via son navigateur.

Le widget accepte aussi des liens profonds: ?transport_line=123, ?transport_stop=STOP_ID et ?transport_direction=HEADSIGN ou ?transport_direction=DIRECTION_ID. Ces paramètres ouvrent directement la ligne, l’arrêt et la direction quand ils correspondent aux données disponibles.

3.8. Temps réel

Le temps réel est optionnel. Le plugin continue à fonctionner avec le seul GTFS statique.

Quand un flux temps réel est configuré et compatible, le module peut aujourd’hui exploiter:

  • TripUpdates;
  • ServiceAlerts;
  • VehiclePositions.

Le temps réel ne remplace pas le théorique. Il vient en surcouche:

  • le théorique reste la base stable;
  • le bloc temps réel montre les prochains départs live;
  • les alertes de service sont affichées séparément;
  • les véhicules apparaissent sur la carte quand la correspondance avec les lignes visibles est possible;
  • si le widget est configuré ainsi, la carte peut limiter l’affichage aux véhicules dont le trip dessert réellement les arrêts suivis localement.

Bonne pratique
Le temps réel doit être considéré comme une amélioration, pas comme l’unique vérité. Si le flux live tombe, la page Transports doit rester utile grâce au GTFS statique.

3.9. Cas d’usage Transports

Cas 1 - Commune avec un seul opérateur

  • Créer une seule source GTFS.
  • Découvrir la commune.
  • Importer les horaires.
  • Ajuster les arrêts de référence par direction.

Cas 2 - Commune avec plusieurs opérateurs

  • Créer une source par opérateur.
  • Conserver un provider key unique par source.
  • Lancer découverte et import pour chaque source.
  • Vérifier que chaque ligne et chaque lieu pointent bien vers la bonne source GTFS.

Cas 3 - Ajouter une ligne d’une commune adjacente

  • ajouter la ligne dans Extra route ids;
  • ajouter les arrêts utiles dans Extra stop ids;
  • relancer découverte puis import.

Ce cas est particulièrement utile quand une ligne ou navette voisine dessert un équipement structurant intéressant pour la commune.

4. Cas d’usage et scénarios recommandés

4.1. Page “Carte interactive” d’une commune

  1. Créer les lieux et circuits dans le module MAP.
  2. Construire la page Elementor avec un widget Carte.
  3. Décider si les filtres restent intégrés ou s’ils sont séparés en plusieurs widgets.
  4. Créer des presets de parcours pour stabiliser le rendu des circuits importants.
  5. Activer les transports si vous voulez une carte mixte.

4.2. Page “Transports” d’une commune

  1. Configurer au moins une source GTFS dans Transports > Horaires.
  2. Lancer découverte et import.
  3. Vérifier ou corriger les libellés des lignes.
  4. Renseigner les arrêts de référence.
  5. Placer le widget Transport Explorer sur la page.
  6. Décider si la carte doit montrer tous les véhicules de la ligne, ou seulement ceux qui desservent les arrêts suivis localement.

4.3. Site multi-communes

En multisite, chaque commune peut vivre sur son propre sous-site. C’est l’option la plus propre pour:

  • isoler ses lignes, lieux, cartes et imports;
  • garder une gouvernance éditoriale plus claire;
  • limiter les effets de bord entre communes.

5. Dépannage rapide

5.1. Une carte n’affiche rien

  1. Vérifier que des éléments MAP existent et sont publiés.
  2. Vérifier les pré-filtres du widget Carte: Univers, Catégories, Thèmes, etc.
  3. Vérifier si la carte affiche bien les lieux et/ou les parcours.
  4. Si vous utilisez des widgets séparés, vérifier que l’Identifiant de groupe est exactement le même partout.

5.2. Les filtres séparés n’agissent pas sur la carte

  1. Vérifier l’identifiant de groupe de tous les widgets concernés.
  2. Vérifier que le widget Carte est bien présent sur la page.
  3. Vérifier qu’il n’y a pas deux cartes avec le même identifiant de groupe par erreur.

5.3. Un parcours ne ressemble pas au style attendu

  1. Vérifier l’affectation du preset dans Styles des parcours.
  2. Vérifier que le parcours visé est bien le bon, surtout si des lignes de transport sont aussi présentes.
  3. Vérifier si un style de catégorie ne prend pas le dessus en absence d’affectation explicite.

5.4. Les transports n’apparaissent pas sur la carte MAP

  1. Vérifier que Inclure les transports est activé sur le widget Carte.
  2. Vérifier que des lignes ou lieux transport existent bien sur le sous-site.
  3. Vérifier la taxonomie Modes.
  4. Vérifier les filtres de type: Lignes de transport peut être désactivé.

5.5. La page Transports n’a pas d’horaires

  1. Vérifier la configuration de la source GTFS.
  2. Lancer Découvrir et synchroniser.
  3. Lancer Importer les horaires.
  4. Vérifier que la ligne est bien reliée à la bonne Source GTFS.
  5. Vérifier que des stop_id ou route_id sont bien présents.

5.6. Le temps réel n’apparaît pas

  1. Vérifier que le temps réel est activé sur la source.
  2. Vérifier que les URL TripUpdates / ServiceAlerts / VehiclePositions sont renseignées.
  3. Lancer Importer le temps réel.
  4. Garder en tête qu’une ligne peut exister sans prédiction live utile au moment précis du test.
  5. Si la carte n’affiche pas un véhicule attendu, vérifier le réglage Afficher tous les véhicules de la ligne sur la carte du widget Transport Explorer.
  6. Un véhicule peut appartenir à une autre branche de la ligne et ne pas desservir l’arrêt suivi localement: dans ce cas, il peut être masqué volontairement.
  7. Si les heures live semblent décalées de 1 ou 2 heures, vérifier Réglages > Général > Fuseau horaire et choisir le fuseau réel du site, par exemple Paris.

Conclusion

Le couple MAP + Transports permet de couvrir deux besoins complémentaires:

  • une cartographie éditoriale souple, très pilotable dans Elementor;
  • une page Transports plus structurée, branchée sur des flux GTFS et éventuellement du temps réel.

Pour rester robuste sur plusieurs communes, gardez une logique simple:

  • le module MAP pour l’éditorial et la mise en scène cartographique;
  • le module Transports pour le réseau, les horaires et les opérateurs;
  • des identifiants de groupe propres dans Elementor;
  • des presets stables pour les parcours importants;
  • des imports GTFS clairement séparés par source et par commune.
